# Inventory service (source of truth for server, console and app)

A shop that sells goods keeps a list of products, prints a small QR tag per
product, and staff scan a tag in the app to sell it; each sale takes stock down
and is recorded. Decisions agreed with the owner on 2026-10-10.

## Rules (settled)
- Service key `inventory` (admin switches it on per business, no charge). Staff permission section `inventory` (one level: sell, create, stock, price, reports, void). Every change records who did it.
- One product = one QR. No sizes/colors: each size or color is its own product.
- Online only. No offline queue.
- A sale is its own record (NOT an invoice). Laawol never charges the customer; it records what the shop took at the counter (payment methods reuse `INVOICE_PAYMENT_METHODS`: cash, zelle, cashapp, venmo, check, card_in_person, other).
- The price is set on the product; at the counter staff may sell at a different price per line (any staff). Keep list price AND sold price AND who sold.
- Selling a product whose count is below the quantity sold is ALLOWED: quantity floors at 0, the line and the product get `countWasOff: true` ("count was off"), the call returns a warning. Never negative.
- Undo a sale = void the whole sale: stock goes back, sale stays in history marked voided (who, when). Nothing is erased.
- Archive is the default removal (hidden from selling and the active list, history kept). Delete is allowed behind a confirmation; sales keep a snapshot of name/price/cost so history survives.
- No receipts. No size, no offline, no customer self-checkout.
- Tag = QR only, 2x1 inch thermal layout, N copies of the SAME code (reprint never changes the code). A customer's phone camera opening the link sees a neutral page with NO product details.
- The QR encodes `https://customer.laawoldigital.com/i/<CODE>`; staff scanning in the app go to the basket.

## Data (Firestore; client read-only via the business read rule used for containers; every write is a callable)
`inventoryItems/{id}`: businessId, name, code (`IT-` + 6 chars from the reduced alphabet in my_flutter_app/lib/services/package_codes.dart / functions generateTrackingCode, unique), priceCents (int), costCents (int|null), quantity (int >= 0), lowStockAt (int|null; item is "low" when quantity <= lowStockAt, and ALWAYS when quantity == 0), category (string, "" ok), photoUrl (string, "" ok), archived (bool), countWasOff (bool), createdAt, updatedAt, createdByStaffId.
`inventoryMovements/{id}`: businessId, itemId, type (`initial`|`add`|`set`|`sale`|`void`), delta (int, signed, actual change after flooring), quantityAfter, byStaffId, note, saleId (""), createdAt.
`inventorySales/{id}`: businessId, lines[{itemId, name, code, quantity, listPriceCents, soldPriceCents, costCents|null, countWasOff}], totalCents (sum of quantity*soldPriceCents), paymentMethod, soldByStaffId, clientRequestId (idempotency, unique per business), voided (bool), voidedByStaffId, voidedAt, createdAt.
Money is integer cents USD, capped like invoice_ledger.js (MAX_CENTS). Audit through the same writeLotLedgerAudit pattern (entityType `inventory_item` / `inventory_sale`).

## Callables (all: requireBusinessPermission(uid, businessId, "inventory") + service enabled check like other services; failures use details.reason codes like the container callables)
- `createInventoryItem {businessId, name, priceCents, costCents?, quantity, lowStockAt?, category?, photoUrl?}` -> {itemId, code}. Writes an `initial` movement when quantity > 0.
- `updateInventoryItem {businessId, itemId, name?, priceCents?, costCents?, lowStockAt?, category?, photoUrl?}` (never quantity).
- `adjustInventoryStock {businessId, itemId, mode: "add"|"set", quantity, note?}` -> {quantity}. `add` adds a positive number; `set` corrects the count (clears countWasOff). One movement each.
- `archiveInventoryItem {businessId, itemId, archived}`; `deleteInventoryItem {businessId, itemId, confirm: true}` (refuses without confirm).
- `recordInventorySale {businessId, clientRequestId, paymentMethod, lines:[{itemId, quantity, soldPriceCents}]}` -> {saleId, totalCents, warnings:[{itemId, reason:"count_was_off"}]}. One transaction; archived or foreign items refused (`item_archived`, `item_not_found`); same clientRequestId returns the same sale (no double sale on a retry).
- `voidInventorySale {businessId, saleId, reason?}` -> {}. Refuses if already voided (`sale_voided`).
- `getInventoryLabelsUrl {businessId, itemId, copies}` -> {url}; copies 1..500; renders through the existing label page handler (`parkingDocument` /d) as a new view `inventoryTags`, format `tag` 2in x 1in, QR only (error correction H).
- `getInventorySummary {businessId, range: "today"|"month", timeZone}` -> {salesCount, itemsSold, revenueCents, costCents (known costs only), profitCents, discountCents (sum of (list-sold)*qty where positive), best:[{itemId,name,quantity,revenueCents}] (top 5), low:[{itemId,name,quantity,lowStockAt}], countWasOff:[{itemId,name}]}. Voided sales excluded. Reads server-side (never the whole sales list in the browser).
Client reads (rules): inventoryItems where businessId (+ code for scan lookup, archived filter), inventorySales where businessId ordered by createdAt desc (paged), inventoryMovements where businessId and itemId.

The app's universal-link / app-link configuration (apple-app-site-association paths, Android intent filter) must include `/i/*`, like `/t/*` for packages.
- Console: Inventory tab (products list with low/countWasOff/archived filters, create/edit, stock add/set, print tags, archive/delete, sales list with void, today/month summary). App: Inventory section (products list + stock add + print tags via getInventoryLabelsUrl, Sell screen = scan -> basket (qty default 1, qty editable, price editable per line, payment method, Sold), sales list with void, today summary + low stock). Scanning the same product twice adds 1 to that line's quantity.

## Backend as built (my_flutter_app/functions: `inventory.js`, `inventory_tags.js`, callables in `index.js`)
Everything above stands. These are the exact details clients can rely on, and the few places the build made a call the contract left open (marked DECISION) or differs from it (marked DEVIATION).

**Gate and errors**
- Every callable: signed in, then `requireBusinessPermission(uid, businessId, "inventory")` (`permission-denied`), then the business must exist (`not-found`, reason `business_not_found`) and have service `inventory` in `enabledServices` (`failed-precondition`, reason `service_disabled`).
- DECISION: `inventory` is NOT in the default service list. A business that never stored `enabledServices` does not have it; an admin must switch it on. (`DEFAULT_BUSINESS_SERVICES` excludes it; `VALID_BUSINESS_SERVICES` and `VALID_BUSINESS_PERMISSIONS` include it.) The staff-permission vocabulary test (`test/business-permission-vocabulary.test.js`) fails until the console and the app lists add `inventory`.
- Every refusal is an `HttpsError` whose message is the English text of `INVENTORY_MESSAGES` and whose `details` are `{reason: <first code>, reasons: [<every code>], ...}`. Validation = `invalid-argument` (all problems at once in `reasons`); `item_not_found` / `sale_not_found` / `business_not_found` = `not-found`; `item_archived` / `sale_voided` / `service_disabled` = `failed-precondition`. Item refusals on a sale add `details.itemIds`.
- Codes: `business_not_found, service_disabled, item_not_found, item_archived, sale_not_found, sale_voided, name_required, name_too_long, price_invalid, cost_invalid, quantity_invalid, low_stock_invalid, category_too_long, photo_url_invalid, nothing_to_update, quantity_not_editable, mode_invalid, archived_invalid, confirm_required, payment_method_invalid, lines_required, lines_too_many, total_too_large, client_request_id_invalid, copies_invalid, range_invalid`.
- All successful answers carry `success: true` besides the contract fields.

**Fields and limits**
- Product: name 1..120 chars; `priceCents` integer 1..MAX_CENTS; `costCents` integer 0..MAX_CENTS or null (empty = null); `quantity` / `lowStockAt` integers 0..1,000,000 (`lowStockAt` empty = null); category <= 60 chars; `photoUrl` empty or an `https://` address (DECISION: plain string, no Storage upload, no storage rule). A product also stores `updatedByStaffId` and `documentToken` (secret behind its tag-printing link). `code` is globally unique (`IT-` + 6 chars, `generateTrackingCode("IT", "inventoryItems", "code")`).
- Archived products can still be edited, restocked, printed and deleted; they cannot be sold.
- `updateInventoryItem` with a `quantity` key is refused (`quantity_not_editable`); with nothing to change `nothing_to_update`. Answer: `{itemId, changed: [field labels]}`.
- `adjustInventoryStock`: `add` needs 1..1,000,000 and the result may not pass 1,000,000; `set` 0..1,000,000. `note` <= 200 chars. Movement `delta` for `set` is after - before (can be 0 or negative).
- `archiveInventoryItem` needs a real boolean (`archived_invalid`); repeating is a no-op. `deleteInventoryItem` needs `confirm === true` (a string "true" is refused). Delete removes only the product: its sales and its movement rows stay (sales keep the snapshot).

**Sale**
- Limits: 1..50 lines, quantity 1..1,000,000 per line, `clientRequestId` 8..100 chars of `[A-Za-z0-9_.:-]`, total <= MAX_CENTS.
- DECISION: a line's `soldPriceCents` must be typed (an empty field is `price_invalid`), and `0` is allowed (a giveaway, shown as a full discount). The product's own list price must be >= 1.
- The sale's document id is `sha256(businessId + NUL + clientRequestId)` (40 hex chars), so the same key can only ever be one sale. A retry answers `{saleId, totalCents, warnings, replayed: true}` with the stored sale's values and writes nothing; the first send has `replayed: false`.
- Two lines of one product in one sale share its stock, in order. Sold-out sales floor at 0 and set `countWasOff` on the line and the product (the flag stays until a `set`).
- ADDITIVE: each sale line also stores `stockDeducted` (what really left the shelf, <= `quantity`). Void puts back exactly that, so a floored sale never invents stock. Movement rows: one per line (`delta` can be 0 when the shelf was already empty), type `sale`, `saleId` set.
- `voidInventorySale` answers `{success, skippedItemIds}`; a product deleted since is skipped (its stock cannot be restored). It adds `voidReason` (<= 300) to the sale and one `void` movement per line whose product still exists. Void works on archived products. Double void: `sale_voided`.

**Tags**
- `getInventoryLabelsUrl {businessId, itemId, copies}`: DEVIATION from "copies 1..500" only in that an out-of-range or missing `copies` is REFUSED (`copies_invalid`), never clamped. Answer `{url}` = `<PARKING_DOCUMENT_BASE_URL or https://laawoldigital.com/d>?t=<item token>&view=inventoryTags&labels=tag&copies=N`. The token is minted once per product and reused. The page (`inventory_tags.js`) is 2 x 1 inch (`@page size 2in 1in`), one tag per page, the QR (error correction H) and nothing else (no code text, no name, no price). The QR holds `<CUSTOMER_CONSOLE_URL or https://customer.laawoldigital.com>/i/<CODE>`. The neutral public `/i/<CODE>` page and the app-link paths are the clients' (not the functions').

**Summary** `getInventorySummary {businessId, range: "today"|"month", timeZone}`
- Answer: `salesCount, itemsSold, revenueCents, costCents, profitCents, discountCents, best[5], low[], countWasOff[]` plus `range, since (ISO start of the range), timeZone (the zone used; an unknown zone reads as UTC), linesWithoutCost, lowCount, countWasOffCount, truncated`.
- DECISION: `costCents` sums quantity x cost over lines with a known cost; `profitCents` = revenue of those same lines - `costCents` (a product with no cost adds revenue but no profit), and `linesWithoutCost` says how many lines were left out, so a screen can say "profit excludes N lines". Voided sales are excluded everywhere.
- `best` = top 5 by pieces, then revenue. `low` and `countWasOff` hide archived products and are capped at 100 entries each (the `...Count` fields are exact). Reads are server-side, cursor-paged (500 per page, at most 40 pages of sales and 40 of products, 60 s budget); `truncated: true` if a bound was hit.

**History and fees**
- `lotLedgerAudit` rows: entityType `inventory_item` (entityId = product id; actions `created, edited, stock_added, stock_set, archived, restored, deleted`) and `inventory_sale` (entityId = sale id; actions `sold, voided`). DECISION: `sold` rows are written already `acknowledged: true` (`writeLotLedgerAudit` accepts an optional `acknowledged`), so counter sales are history but do not flood the Today "Needs attention" feed; all other actions are unacknowledged like the container ones.
- No charge and no platform fee: inventory never touches `platform_fees.js` or `business_billing_plan.js` (both are keyed by a charge's service, and a sale moves no money through Laawol). It needs no verification document and is not in `COLLECTION_TO_SERVICE` (the platform-admin write path does not apply: every write is a callable).

**Rules and indexes** (`firestore.rules`, `firestore.indexes.json`): `inventoryItems`, `inventorySales`, `inventoryMovements`: read `lotLedgerRead(resource.data.businessId)`, write false. Composite indexes: items (businessId, code), (businessId, archived), (businessId, name), (businessId, archived, name); sales (businessId, createdAt desc); movements (businessId, itemId), (businessId, itemId, createdAt desc). Clients must always include `where businessId == mine`; the `console-query-rules` test pins the shapes in the "Client reads" line above plus ordered-by-name and archived filters.

**Tests**: `test/inventory.test.js` (pure), `test/inventory-callables.test.js` (`npm run test:inventory`, Firestore emulator), plus inventory cases in `test/firestore-rules.test.js` and `test/console-query-rules.test.js`.

## Console notes (admin_web: what the web client assumes of the callables)
- `updateInventoryItem`: a cleared cost or low-stock number is sent as `null` (and only when the product had one); category and photoUrl clear with `""`. The count is never sent.
- `createInventoryItem` answers `{itemId, code}`; the console opens the tags dialog on it for "Save & print tags".
- Failure reasons the console words itself (`details.reason`): `item_archived`, `item_not_found`, `sale_not_found`, `sale_voided`, `confirm_required`, `service_not_enabled`, plus the validation codes `name_required`, `price_invalid`, `cost_invalid`, `quantity_invalid`, `low_stock_invalid`, `photo_url_invalid`, `copies_invalid`, `payment_method_invalid`. Any other reason falls back to the server's own message.
- Reads needing composite indexes in `firestore.indexes.json`: `inventorySales` (businessId ASC, createdAt DESC) and `inventoryMovements` (businessId ASC, itemId ASC, createdAt DESC). `inventoryItems` uses `businessId ==` + `archived ==` only (no composite).
- A voided sale may carry `voidReason`; the console shows it when present.
- Public tag page: `/i/<CODE>` is rewritten by `admin_web/public/.htaccess` to `/?service=item-tag` (the code is dropped); the page is also recognised from a bare `/i/<CODE>` path. `apple-app-site-association` lists `/i/*`; the Android intent filter (`AndroidManifest.xml`, `pathPrefix="/i/"`) is the app's to add.

**Console notes (v2: categories and stores, admin_web)** - what the web client assumes on top of the "Categories and stores (v2)" contract below:
- Every v2 request carries `businessId` (like the v1 ones), including `createInventoryCategory`, `renameInventoryCategory`, `archiveInventoryCategory`, `createInventoryStore`, `updateInventoryStore`, `archiveInventoryStore`, `transferInventoryStock` and `setInventoryStaffAccess {businessId, userId, homeStoreId, allStores}` (`userId` = the staff member's uid). `createInventoryCategory` answers `{categoryId}`, `createInventoryStore` answers `{storeId}`.
- Product requests: a category chosen from the list is sent as `categoryId` only; a typed name (legacy product, or a business whose category list could not be read) is sent as `category` exactly as in v1; clearing sends `category: ""` plus `categoryId: ""` when the product had an id. `createInventoryItem` in a multi-store business sends `stock: {storeId: n}` (stores above zero only, no `quantity`); a single-store business still sends `quantity`. `adjustInventoryStock` / `getInventorySummary` / `recordInventorySale` carry `storeId` only in a multi-store business (the console never sells). `updateInventoryStore` sends only the fields that changed (a cleared address or phone is `""`).
- Single-store mode is decided in the browser from `inventoryStores` (two or more with `archived != true`). The owner always gets a "Stores" button, even with 0 or 1 store: it is the only way to add the second store that turns multi-store mode on. Nobody else sees anything about stores until then.
- Who sees what: the owner (`role == businessOwner`) and staff with `inventoryAllStores == true` on their `users/{uid}` profile see every store, with the store filter, the By store block and Move stock; other staff are scoped to `inventoryHomeStoreId` (their stock rows are read with `storeId ==` home store, their sales with `storeId ==` home store ordered by `createdAt` desc) and get no filter. Staff in a multi-store business with no valid home store see a notice instead of the lists.
- Low stock per store: a store's count at or below `lowStockAt`, or 0, is low for that store **when that store has a count row for the product**. A store with no `inventoryStock` row reads 0 and is NOT flagged low (otherwise adding a store would flag every product at once). The Main store a record belongs to when it has no `storeId` (old sales) is the store with the earliest `createdAt`.
- Sales by store: all-store viewers read the sales unfiltered (existing index) and narrow by store in the browser, so a sale without `storeId` (from before stores) counts under the Main store; this narrows the loaded pages only. Single-store staff need the composite index `inventorySales`: `businessId ASC, storeId ASC, createdAt DESC`. `inventoryStores` / `inventoryCategories` are read whole by `businessId`; `inventoryStock` by `businessId` (+ `storeId`), whole. All three must be readable by every member with the Inventory permission (stock and sales narrowed to the home store for staff without all-stores access).
- Summary: `byCategory` (every category, `categoryId: ""` is the Uncategorized row), `byStore` (all-store callers only) and `low[].storeId/storeName` are read when present and sorted by money in the browser; an answer without them (a v1 server) just shows no blocks.
- Failure reasons the console words itself, in addition to the v1 list: `category_name_required, category_name_taken, category_not_found, store_name_required, store_not_found, store_archived, store_has_stock, store_not_allowed, home_store_required, same_store, insufficient_stock, owner_only`; the console also checks the obvious ones before the call (blank names, a name already used, same store, more than the source store holds when its count is known, no home store for staff who do not work in all stores).

**Switching it on (platform admin)**: `setBusinessInventoryService {businessId, enabled: boolean}` (functions/index.js; pure plan in `inventory.js` `planInventoryService`). Gate: signed in, then the same `businesses` admin capability as `createAdminBusiness` (owners and other admin roles get `permission-denied`). Missing business: `not-found`; a non-boolean `enabled` or missing id: `invalid-argument`. It adds or removes only `inventory` in `businesses/{id}.enabledServices` (other services and the `VALID_BUSINESS_SERVICES` order kept), is a no-op (`changed: false`, no write, no audit row) when already in that state, writes an `adminAuditLogs` row (`inventory_service_enabled` / `inventory_service_disabled`, metadata.service "inventory") and refreshes the business snapshot copies like other admin edits. Console: the business detail header in the admin console shows an "Inventory service" pill and a "Switch Inventory on/off" button (confirm + confirmFr, success message through `runAction`); the featured-business editor still hides the checkbox. `npm run test:inventory` now starts the Auth emulator too (an admin profile check reads the Auth account).

**Requesting it (public application form)**: the partner application page (`public_site/partner.html`) has an "Inventory" card (unchecked by default, English + French) whose state is sent as a separate boolean `requestInventory`, never inside `enabledServices`, and it does not count toward "choose at least one service". `submitBusinessApplication` reads it strictly (only the boolean `true`; anything else is false), still strips `inventory` from the services, and stores `requestedInventory: true|false` on the `businesses` doc, the `businessApplications` doc and the admin notification. `setBusinessInventoryService` sets `requestedInventory: false` in the same write when it switches Inventory on (and clears a stale true flag even when it was already on). The admin console shows a read-only "Requested Inventory" badge in the businesses list and next to the Inventory service switch while `requestedInventory === true` and Inventory is not on (`businessRequestedInventory` in `admin_web/src/lib/inventory.ts`). The flag never turns anything on.

# Categories and stores (v2) - contract, agreed 2026-10-11

Settled with the owner. Two additions on top of everything above; **nothing existing may break** (see "Compatibility").

## Categories
- Each business keeps its own list (`inventoryCategories/{id}`: businessId, name, nameKey = lowercased trimmed name, unique per business, archived, createdAt, createdByStaffId). Shared by all stores.
- A product picks one category from the list or adds a new one while creating/editing. The free-text `category` field on a product becomes a **snapshot of the chosen category's name** plus `categoryId`. Legacy typed categories are matched into the list (find-or-create by nameKey) the first time they are read/written (no big-bang migration; a bounded, idempotent conversion callable is fine).
- Renaming a category renames it everywhere shown (items keep a `category` name snapshot updated by bounded batches; sales lines keep the `categoryId` + name snapshot taken at sale time). Categories are archived, never deleted; products keep their category.
- Reports: the Today / This month summary gains `byCategory: [{categoryId, name, itemsSold, revenueCents, profitCents}]` sorted by revenue desc (all categories, "Uncategorized" for none). Voided sales excluded; revenue = price actually charged; profit counts only lines with a known cost (same rule as today). Legacy lines without a snapshot use the item's current category (bounded lookups).

## Stores
- A store: `inventoryStores/{id}`: businessId, name (required), address, phone (optional), archived, createdAt, createdByStaffId. Only the **owner** creates/edits/archives stores. A store with stock cannot be archived (`store_has_stock`); move it first.
- **Single-store businesses see nothing about stores.** A business with zero or one active store is "single store": today's behaviour and screens, no store pickers/columns/filters. Existing products and their counts simply belong to the implicit "Main store". The first time the owner adds a second store, the Main store becomes a real store doc ("Main store", renameable) and every existing product's count moves under it.
- One product list and one QR per product for the whole business. **Stock is counted per store.** `inventoryItems.quantity` stays as the **total across stores** (old clients read it and it keeps working); per-store counts live in `inventoryStock/{itemId}__{storeId}` {businessId, itemId, storeId, quantity (>=0), countWasOff, updatedAt}. Both are changed in the same transaction. Pick the cheapest design that needs no big-bang migration and keep single-store businesses on the existing fast path; write the chosen model down in this file BEFORE coding ("Backend as built (v2)").
- Staff: `inventoryHomeStoreId` (string) and `inventoryAllStores` (bool) on the staff member's business membership/user record, set only by the owner (`setInventoryStaffAccess {userId, homeStoreId, allStores}`; allStores=true means owner-like store access). The business owner always has all stores. A staff member with no home store in a multi-store business cannot sell until one is assigned (`home_store_required`).
- **Selling:** `recordInventorySale` takes an optional `storeId`. Omitted -> the caller's home store (single-store business: the Main store). A store other than the caller's home is allowed only with allStores/owner (`store_not_allowed`). Sale documents and lines record `storeId` (+ store name snapshot). Voiding restores stock to the sale's store. The "count was off" / floor-at-zero rules apply per store. **Old app builds (1.0.9) send no storeId and read only `quantity`: they must keep working exactly as before** (server picks the store as above).
- **Transfers:** `transferInventoryStock {itemId, fromStoreId, toStoreId, quantity, note?}`: owner and allStores staff only. One transaction: from -1..n, to +n, one movement per side sharing a `transferId`; refuses more than the source holds (`insufficient_stock`) and same-store (`same_store`). Totals unchanged.
- Stock changes (`createInventoryItem` starting counts, `adjustInventoryStock` add/set) take a `storeId` (default as above). `createInventoryItem` accepts `stock: {storeId: qty}` for multi-store businesses (`quantity` still works for single-store).
- Low stock: ONE `lowStockAt` per product, checked **per store** (a store's count at or below it, or 0, is low for that store). Lists/summaries show the store name on low-stock rows in multi-store mode.
- **Visibility (enforced on the server AND in Firestore rules, not only in the UI):** a staff member without allStores/owner sees only their home store's stock rows and their store's sales; owners/allStores staff see everything with a store filter (All stores / one store). `getInventorySummary` takes an optional `storeId` ("" or omitted = all stores, only for owner/allStores; staff always get their home store) and adds `byStore: [{storeId, name, salesCount, itemsSold, revenueCents, profitCents}]` for all-store callers in multi-store mode.

## New / changed callables (all: inventory permission + service on, like the others)
`createInventoryCategory {name}` -> {categoryId}; `renameInventoryCategory {categoryId, name}`; `archiveInventoryCategory {categoryId, archived}`;
`createInventoryStore {name, address?, phone?}` -> {storeId}; `updateInventoryStore {storeId, name?, address?, phone?}`; `archiveInventoryStore {storeId, archived}` (owner only);
`setInventoryStaffAccess {userId, homeStoreId, allStores}` (owner only); `transferInventoryStock` (above);
changed: `createInventoryItem` / `updateInventoryItem` (`categoryId`, or a `category` name to find-or-create; `stock`), `adjustInventoryStock` (+`storeId`), `recordInventorySale` (+`storeId`), `getInventorySummary` (+`storeId`, `byCategory`, `byStore`).
Client reads: `inventoryCategories` where businessId; `inventoryStores` where businessId; `inventoryStock` where businessId (+ storeId); the existing three collections gain `storeId` where relevant. Refusal codes in `details.reason` as before; new: category_name_required, category_name_taken, category_not_found, store_name_required, store_not_found, store_archived, store_has_stock, store_not_allowed, home_store_required, same_store, insufficient_stock, owner_only.

## Compatibility (hard rules)
1. A request shaped like the v1 contract (no storeId, no categoryId, `category` text, `quantity`) works unchanged for single-store AND multi-store businesses.
2. No existing document is rewritten in bulk; conversions are lazy, idempotent, bounded.
3. Rules and indexes for the new collections ship with the same change; every new client read has its composite index and a test in console-query-indexes / console-query-rules.
4. Every new string in English and French; US-style dates; money in cents USD.
5. Order of delivery: server + console first, app screens in the next app release (the app code may be written now and merged, but is NOT released with this server deploy).
