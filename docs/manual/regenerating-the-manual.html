Regenerating the manual

Laawol-Business-Onboarding.pdf is the guide handed to businesses when they join. Its screenshots come from the live console, so it needs regenerating whenever the console changes materially.

Everything lives in docs/manual/:

FileWhat it is
business-onboarding.html The manual's source. Edit this to change wording or structure.
capture-console.mjs Captures every console section as a PNG.
capture-extra.mjs Captures sub-sections the section pass misses — see step 2b.
screenshots/ Captured images. web-* console, app-* mobile.
Laawol-Business-Onboarding.pdf The rendered output — the file you send to businesses.

STEP 1Copy a signed-in Chrome profile

The console requires a sign-in, so the capture reuses an existing session. It runs against a copy of the profile — that way the session carries over without holding a lock on the profile Chrome is using, and you can keep working while it runs. 

# Skip the caches, or the copy is well over a gigabyte
SRC="$HOME/Library/Application Support/Google/Chrome"
DST=/tmp/chrome-capture-profile
rm -rf "$DST" && mkdir -p "$DST/Profile 1"
cp "$SRC/Local State" "$DST/"
rsync -a --exclude 'Cache' --exclude 'Code Cache' --exclude 'GPUCache' \
      --exclude 'Service Worker/CacheStorage' --exclude 'blob_storage' \
      "$SRC/Profile 1/" "$DST/Profile 1/"

Check that Local Storage, IndexedDB, and Cookies made it into the copy — those carry the session. If the capture comes out showing a sign-in page, one of them is missing.

STEP 2Capture the console

node docs/manual/capture-console.mjs \
  /tmp/chrome-capture-profile \
  docs/manual/screenshots

It launches headless Chrome, clicks each sidebar section in turn, waits for Firestore rows to stream in, and writes one PNG per section. Roughly two minutes for twelve sections.

Capture from an account with real data. A fresh business has empty queues, and a manual full of empty panels teaches nothing. The current screenshots come from an account with live shipments, listings, and reviews.

STEP 2BCapture the sub-sections

node docs/manual/capture-extra.mjs \
  /tmp/chrome-capture-profile \
  docs/manual/screenshots

Step 2 clicks a sidebar item and shoots the viewport, so it only ever captures the top of a long page. Services & coverage is really four stacked sections — services, rules, locations, coverage — and only the first is above the fold. This pass scrolls to each one by its heading and captures it.

Scroll by the smallest matching element, not the first. <body> contains every heading's text, and so does the sidebar, so "first element containing the text" scrolls nowhere. The script filters to the element with no matching child. If a capture comes back showing the top of the page, that filter stopped matching — the heading text changed.

STEP 3Capture the mobile app

Boot a simulator with the app installed and signed in as a customer:

xcrun simctl list devices | grep Booted
xcrun simctl io <UDID> screenshot docs/manual/screenshots/app-01-home.png

This reads the simulator's framebuffer directly, so it needs no screen-recording permission and never captures anything outside the simulator.

STEP 4Render the PDF

cd docs/manual
"/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" \
  --headless=new --disable-gpu --no-pdf-header-footer \
  --virtual-time-budget=20000 \
  --user-data-dir=/tmp/pdfprof \
  --print-to-pdf="$PWD/Laawol-Business-Onboarding.pdf" \
  "file://$PWD/business-onboarding.html"

Chrome writes the PDF and then does not exit. The file is complete before it hangs — wait for it to appear, then kill the process. Don't take the hang as a failure and rerun; you'll just hang again.

Why it is scripted rather than screenshotted by hand

Two problems make manual capture the wrong approach, and both bit during authoring.

A screen grab photographs whatever is on screen

screencapture captures what is genuinely visible, so it depends on the right tab being frontmost and will happily include other windows, notifications, or private content. During authoring it caught an unrelated browser tab, the desktop, and a password prompt — three captures that had to be deleted. Headless capture makes that impossible: nothing outside the page is ever in frame.

The console has no URL routing for tabs

The active section is React state, not a URL. So a one-shot --screenshot against a URL can only ever produce the Today tab, no matter which section you want. capture-console.mjs drives Chrome over the DevTools Protocol instead: it clicks each sidebar item and captures what renders. Node 22 ships a WebSocket, so this needs no dependencies.

Changing the manual's content

Edit business-onboarding.html and re-run step 4. You only need steps 1–3 when the console's appearance has actually changed.

The guide is deliberately written in setup order — approval, verification, services, destinations, payouts, staff — because that is the sequence a new business experiences, and each step genuinely depends on the one before it. The operational sections come afterwards and use the populated account so the screenshots show something real. Keep that shape if you extend it.

Known gaps

  • Parking has no screenshot. The captured business doesn't offer it, so the console correctly shows "Not offered". The guide covers parking in text only. To screenshot it, enable Car parking in Services & coverage on the capture account first.
  • Shared barrels is deliberately absent. The panel is gated on appConfig/client.sharedBarrelsEnabled (lib/feature-flags.ts), which is not set in production — so the feature is off for every business, not just the capture account. It stays out of the guide until that flag ships. The Destinations tab is reachable only from inside that same gated block, which is why country coverage is documented from the 4 · Coverage section of Services & coverage instead.
  • This is the business half. A customer-facing guide would be a separate document; the app-* screenshots already captured would carry over to it.
